# Architecture

```text
 Phone app (apps/)                 Staff website (web/)
   students and guides               Chats / Chats + Updates staff
        │ bearer token                     │ httpOnly cookie
        └──────────────┬───────────────────┘
                       ▼
        Bell Space server (server/), one Node process
          /v1/ API · /v1/live WebSocket hints · serves web/dist at /
                       │
                       ▼
                  PostgreSQL
          data and all access rules (server/migrations/)
```

## The parts

| Part | Stack | Notes |
| --- | --- | --- |
| `apps/` | Expo SDK 58, React Native 0.88, Reanimated, react-native-svg | Map, directions and live-location experiment work offline with no backend. `src/backend/mode.ts` picks the backend for sign-in, Chat and Updates. |
| `server/` | Node 22.18+ (runs `.ts` directly), Fastify 5, `pg`, `ws` | One service. Development and tests use PGlite (real Postgres in-process) when `DATABASE_URL` is unset. |
| `web/` | React 19, Vite | Built to `web/dist`, served by the server, so there is no second server and no cross-origin setup. |
| `shared/` | Plain TypeScript | API shapes, labels, limits and staff types, imported by relative path. |
| `maps/` | SVG | Generated by `tools/campus-trace/campus.py`; the app imports them through `apps/svg-transformer.cjs`. |

## Access rules live in the database

The server signs the caller in, then runs each request in one transaction as the
`app_user` role with `app.account_id` set. Row-level security and checked
functions in `server/migrations/001_init.sql` decide what each account may see or
change. Route code only checks input shape and calls those functions, so a bug in
the server or website cannot grant access the rules forbid. The rules are tested
in `server/tests/rules.test.ts` against the real migration.

## Accounts

* Students (and guides, who are students with a guide profile) use the app.
* Staff use the website as one of two types: **Chats**, or **Chats + Updates**
  (which also manages accounts and the supervision setting). The server stores
  three permissions (`support`, `updates`, `manage_accounts`).
* Passwords are scrypt hashes; sessions are random tokens stored hashed and can be
  revoked. District sign-on will replace passwords (`accounts.external_id`).

## Support chat (CLEAR 2.0)

```text
submitted → staff assign a guide → with_guide → guide marks done → follow_up → resolved
    ↑                                   │
    └──────── guide declines ───────────┘
submitted → staff keep it (sensitive) → with_staff → resolved
```

No automatic matching, no messaging outside an assigned request, and sensitive
requests never reach guides. The supervision setting (`all_requests` or
`reported_only`) controls whether Chats staff read every thread; every staff view
is recorded. Details: [backend-plan.md](backend-plan.md).

## Live updates

Database triggers call `pg_notify` with ids only. The server forwards a hint over
`/v1/live` to each connection whose account may see the row (checked in the
database as that account). Clients then fetch through the API, so message text
never travels over the socket.

## Map

All floors share one campus frame. The SVGs in `maps/` are the source of truth;
the app extracts geometry at bundle time and draws labels as native text, with
level-of-detail by zoom. Routes come only from `apps/src/navigation/data/` and use
only checked doors and paths. Details: [campus-map.md](campus-map.md) and
`apps/src/map/README.md`.

## Compatibility

The API is versioned under `/v1/` and only grows, so older app versions keep
working while students update. Website and server changes take effect on deploy.
